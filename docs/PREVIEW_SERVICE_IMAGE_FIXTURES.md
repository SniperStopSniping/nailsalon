# Preview service-image fixtures

This runner manages synthetic Preview-only data for service-image visual review. Never use it against Production. It does not load dotenv files, run migrations, deploy code, or call provider APIs.
Run `npm run db:fixture:preview -- <plan|apply|verify|reset>`. Every command connects only after static validation, then checks the live TLS session, non-elevated role, serializable transaction, exact 64-migration ledger ending in `0063_booking_policy_acknowledgments`, schema, and fixture ownership. `reset` also needs `LUSTER_PREVIEW_FIXTURE_RESET_CONFIRM=DELETE_SYNTHETIC_PREVIEW_FIXTURES`. Required process inputs include a process-scoped PostgreSQL connection, `LUSTER_PREVIEW_FIXTURE_ENV=preview`, exact database/host/TLS/application-name markers, `LUSTER_PREVIEW_FIXTURE_VERSION=service-images-v1`, `LUSTER_PREVIEW_FIXTURE_CONFIRM=CREATE_SYNTHETIC_PREVIEW_FIXTURES`, and an independently prepared `LUSTER_PREVIEW_TARGET_FINGERPRINT`. The fingerprint is SHA-256 of `lowercase-host|5432|role|database`; do not calculate the expected value from the connection input in the same invocation. Supply inputs directly through the supervised process environment—never create a runtime dotenv file.
The deterministic scope is two salons, two locations, twelve image-bearing services, two technicians, twelve assignments, two add-ons, two add-on rules, one unmapped synthetic admin, and two owner memberships. The default salon omits `showServiceImages`; the comparison salon stores `showServiceImages=false`. Plan and all output contain aggregate counts only. Public booking review needs no provider identity. Optional Settings access requires a separately created Clerk Development user ID plus `LUSTER_PREVIEW_CLERK_ENV=development` and `LUSTER_PREVIEW_ADMIN_CONFIRM=MAP_SYNTHETIC_DEVELOPMENT_USER`; the runner validates and stores the ID without logging or calling Clerk. A Settings save creates application audit history, so reset will safely refuse until those non-allowlisted rows are reviewed separately.
