# AI setup add-ons checkpoint

This phase extends the shared business draft using Luster’s existing `add_on` and `service_add_on` records. It does not create a second service catalog. It follows `1e276e4c` on `codex/ai-business-setup`; nothing was pushed, merged or deployed.

Owners can propose fixed-price or per-unit extras in chat, review prices, extra minutes and eligible services, edit those values manually, accept the proposal, and approve the exact publication revision. An explicit add-on price correction also works from the Website composer under the existing narrow price-edit boundary. New relationships are optional and catalog-priced. Group membership, required/conditional selection, manual-confirmation pricing, link quantities and ordering are preserved. For an extra with those rules, changing its service choices, active state or quantity rules remains in the existing service library; the draft rejects such changes rather than silently simplifying them. Ambiguous uploaded items still require clarification before being classified as extras.

`add-ons.ts`, `AddOnEditor.tsx` and `AddOnBookingSummary.tsx` provide validation and the same readable proposed catalog in Details, review, standard preview and isolated custom preview. Preview still cannot create appointments. Availability examples explicitly cover the base service only. Pending extras open automatically, and the publication checklist links directly to setup review.

`drafts.server.ts` reads the canonical catalog into the draft, hydrates older immutable revisions without rewriting history, and locks catalog/link rows during publication. `add-on-publication.server.ts` changes only supported catalog fields and explicitly selected links inside the existing approved transaction. It leaves omitted catalog records and inactive-service relationships alone. Link insertion conflicts abort publication. `publication-identities.server.ts` resolves restored draft identities through the original receipt and lineage. Additive migration `0110_setup_add_on_publication.sql` adds an empty-default `add_on_ids` receipt map; no destructive migration or existing appointment update is involved. Applied only to attested local development, disposable PostgreSQL and in-memory test databases.
