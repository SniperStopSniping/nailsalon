# Production operator expense boundary — 2026-10-18

Prepaid salon credits are not the operator's provider-spending authorization. Production generation now also requires `CUSTOM_SITE_PRODUCTION_BUDGET_CAD`, an explicit cumulative operator limit, and uses the fixed `production-custom-websites-v1` ledger. It has no automatic renewal, time-based reset, per-salon allowance or model/browser-selected identity. No production cap has been configured or activated by this change. The CAD80 testing limit and its existing local/hosted allocations remain separate and unchanged.

Each paid call reserves its conservative provider expense inside the existing salon/account/budget transaction before transmission. All salons contend on the same budget-row lock. The effective ceiling is the smaller of the environment value and the already-persisted cap, so changing an environment variable cannot raise or replace a budget. Failed and unknown-usage calls remain counted even when customer credits are returned. Older production calls with null budget identities are included in the cumulative expense, avoiding a fresh allowance on upgrade. Aggregation occurs in PostgreSQL instead of loading all historical calls into application memory.

The dedicated key and valid expense configuration are now required before advertising new credit purchases. The authenticated wallet read and checkout entry additionally check available operator expense; exhaustion disables new purchases before any Stripe price/customer/session operation. Existing payment reconciliation/refunds remain available, and the final model-call transaction independently rechecks exact available expense. A purchase-readiness check cannot promise that capacity/provider service remains available indefinitely after checkout; existing customer credits are retained during an outage or operator pause.

Migration `0112_ai_operator_expense_budget.sql` extends the existing SQL cap constraint only for the fixed production ledger identity. It neither creates nor changes a budget row, balance, reservation or appointment. All other ledgers keep the CAD80 SQL maximum. The existing int4 micro-CAD column supports a maximum configured production total of CAD2147.483647; parsing uses exact six-place decimal arithmetic and rejects overflow, exponents, negatives, missing values and extra precision. Increasing the storage ceiling needs a separate reviewed migration. Raising an active budget requires explicit operator authorization and a reviewed update to its persisted limit; never delete expense history or release unknown usage to regain capacity.

The migration was exercised in disposable PGlite/PostgreSQL only. It has not been applied to development, hosted Preview or Production. Before production enablement, deploy/review this code and migration through the normal protected-main path, apply the authorized migration, confirm matching live provider/payment environment configuration, then explicitly approve/configure the cumulative expense ceiling. The existing trial key and testing budget do not authorize production provider use. Rollback disables new AI generation/purchases with their existing flags; published sites, original bookings, credit balances and payment reconciliation remain intact.
